# Building trains more efficiently with AI at Alstom

**Alstom loses about 3 points of gross margin to project execution and industrial inefficiencies: 13.3% booked in FY 2025/26, against 16.0–16.5% without them.**

![Alstom slide: Rolling Stock execution and industrial inefficiencies impacting margins for too long](image.png)

*Source: Alstom investor presentation, slide 51.*

The slide names three causes: poor end-to-end coordination across supply chain and logistics, late engineering changes that slow the ramp-up to serial production, and frequent production rescheduling.

This repo explores how AI can help recover that margin.

## The demo

Three noisy files describe a family of six train variants: an engineering BOM, a purchasing item list and free-text technical notes (`data/raw/`, generated by `synth/`). The demo reconciles them and answers which sub-assemblies are reused, reusable, blocked or specific.

There are three stores. Two are kept, one is rebuilt:

1. **`data/raw/`** is never changed.
2. **`data/claims.jsonl`** is the claim log. Each line is one statement about the raw data ("these two spellings are one part", "this part is superseded by that one"), with who made it (a rule, the agent or a person) and its evidence. Lines are only ever appended.
3. **`out/pilot.db`** is a SQLite database computed from the two above by `pipeline/build.py`. It can be deleted at any time. To change it, append a claim and build again.

The design is described in `.claude/.archived_plans/demo-pipeline-architecture.md`.

| Folder | What it holds |
|---|---|
| `pipeline/` | The claim log and its checks, the rules that write the mechanical claims, and `build()`. Standard library only, no model |
| `reconcile/` | The agent: four tools (describe the tables, read-only SQL, append a claim, append a claim in a person's name), and the batch and terminal entry points. It has no shell and no file tool, so these four are its only access to the data, and none of them asks for approval |
| `skills/` | The agent's skills. `reconciliation/SKILL.md` is what it is told, and is in its system prompt from the start |
| `jean-code/` | Submodule: the agent framework and the Streamlit app, including the Claims page |
| `tests/` | `uv run pytest` |

### Run it

The agent needs an OpenRouter key in `.env` (`OPENROUTER_API_KEY=...`). The first two commands need no key and no model.

```
uv sync
uv run python -m pipeline.rules                                  # the rules append their claims to data/claims.jsonl
uv run python -m pipeline.build                                  # compute out/pilot.db from the raw files and the claims
uv run --env-file .env python -m reconcile.batch --max-cost 2    # the agent settles the open items, one per turn
uv run --env-file .env python -m reconcile.chat                  # ask the agent questions in the terminal
```

The app, with the agent on the Agent page, the raw files on the Raw data page, the database the agent queries on the Reconciled data page and the claim log on the Claims page. It builds the same agent as the two commands above (`reconcile.agent:reconciliation_agent`):

```
uv run --env-file .env streamlit run jean-code/src/app.py
```

### The rules

The rules are in one file, `pipeline/rules.py`: one function per rule, listed in `RULES`. Each rule reads the raw files and returns claims. Its docstring is its description.

```
uv run python -m pipeline.rules --list             # each rule, its description and the claims it makes
uv run python -m pipeline.rules --show near_key    # the claims one rule makes now, compared with the log
```

Neither command writes anything. To change a rule, edit its function and run `--show` on it. Each claim is printed on one line with a mark: `+` the claim is not in the log yet, `-` the claim is in the log and the rule no longer makes it, `~` the claim is in the log with the other standing (asserted or proposed), no mark when nothing changed.

The log is only appended to. Running the rules after a change adds the `+` claims and leaves the `-` and `~` claims in the log as they were.

Replays leave claims out, to see what they changed:

```
uv run python -m pipeline.build --made-by rule       # the rules alone, without the agent
uv run python -m pipeline.build --without-notes      # without any claim that rests on a note
uv run python -m pipeline.build --up-to 432          # the first 432 claims only
```

## Example questions

Questions the demo agent should be able to answer on the generated train family (six variants, `V1` to `V6`). Each takes several steps: a comparison across variants, a walk from a component up to the variants that use it, or a cost roll-up.

The answers are computed from `data/clean/`, the generated files before noise is added, so they are what the agent should find once the noisy files in `data/raw/` are fully reconciled. The script is `.experiments/44_multi_step_questions.py`.

Cost answers need a person first. The noisy files give some parts two different prices, and others none. The database does not pick: it leaves the totals that depend on those parts empty, says which parts block them, and the agent asks which price holds. The cost figures below are what it gives once those prices are settled.

One more difference from the clean files: once a note says two references are one part (`ST-4100` and `MP-4418`, `HC-6001` and `CL-0931`), the database treats them as the same reference. The first question then reports 38 under the same reference and 2 under another, with the same 40 in total.

| Question | Answer |
|---|---|
| Which sub-assemblies of `V1` can I reuse in `V2`? | All 40 have the same content in `V2`. 36 keep the same reference. 4 are under another one: `HC-6001` as `CL-0931`, `KP-0457` as `DC-3001`, `RG-0212` as `TC-8100`, `ST-4100` as `MP-4418`. 4 contain an obsolete or superseded part: `DR-1043`, `FC-6100`, `HT-5300`, `KP-0457`. |
| `V3` and `V4` differ only by speed class (160 against 200 km/h). What differs, and is each difference justified? | 26 sub-assemblies are the same. `LR-1500` has the same content as `PB-2281`. 4 are nearly the same: the air duct (`VL-905` added) and the left door leaf (`JT-305` added) are both required for 200 km/h by a note, while the glazed partition (`BK-367` added) and the sliding step (12 bolts against 16) have no note. The other 9 are different designs. |
| `TH-415` is superseded. What is affected, and is the replacement already in use? | It is in `HT-5300` on all six variants. Its replacement `TH-450` is already used in `TC-8437` on `V4` and `V6`. The unit cost goes from 59.43 to 78.88 EUR. |
| What does the door system cost in each variant? | `V1` 229,555.56 EUR, `V2` 267,814.82, `V3` 331,683.36, `V4` 356,572.22, `V5` 439,188.24, `V6` 515,070.20. Every line has a price. |
| What would `V5` save by using seat frame `SF-9020` in place of `SF-9064`? | 11.48 EUR per unit, at 200 per train: 2,296.00 EUR per train. |
